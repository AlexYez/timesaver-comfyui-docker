## Цель

Нужна переносимая среда ComfyUI для генерации изображений и видео на арендуемых GPU:

- свежий ComfyUI и встроенный Manager нового поколения;
- заранее установленные ноды Timesaver;
- возможность ставить дополнительные ноды через Manager;
- быстрый переход между доступными GPU и облачными сервисами;
- сохранность моделей, workflow, настроек и результатов независимо от жизненного цикла Pod;
- минимальные расходы во время простоя.

## Репозитории и образ

- Исходный код: <https://github.com/AlexYez/timesaver-comfyui-docker>
- Docker Registry: `ghcr.io/alexyez/timesaver-comfyui-docker`
- Подвижные теги: `latest` и `cu128`
- Датированный тег проверенной локально сборки: `cu128-20261005`

GitHub Actions собирает образ раз в неделю, по воскресеньям в 03:17 UTC, а также после изменения Dockerfile, entrypoint, списка встроенных нод или самого workflow сборки. До 20 сентября 2026 года сборка запускалась ежедневно.

Тег `cu128` перемещается на последнюю успешную сборку. Датированный тег остаётся точкой восстановления. Уже запущенный Pod не обновляется автоматически: новую сборку получает новый контейнер.

BuildKit-кэш GitHub Actions переведён с `mode=max` на `mode=min`. При проверке обнаружилось 29 старых записей общим объёмом 11,397 ГиБ — примерно на 1,4 ГиБ выше отдельного бесплатного лимита Actions Cache в 10 ГиБ. 20 сентября 2026 года все 29 старых записей удалены; после очистки объём кэша составлял 0 ГиБ. Следующая сборка создаст новый компактный кэш.

### Почему Manager не отмечает встроенные паки как Installed

Три пака попадают в `custom_nodes` напрямую из Docker, а не через установочную операцию Manager. Поэтому ComfyUI загружает ноды, но Manager может показывать пакеты как неустановленные.

Это не мешает работе. В проверенном Pod сервер загрузил 984 класса нод, из них 76 совпали с пакетами Timesaver и CosyVoice. Не следует повторно нажимать Install для этих трёх пакетов: возможны конфликт и дублирование файлов.

Дополнительные ноды, установленные через Manager, он отслеживает обычным способом. Их обновляют кнопкой Update. Docker-пересборка такие ноды не обновляет.

Отдельная будущая задача — перевести установку трёх встроенных пакетов на Registry-механизм, чтобы Manager показывал их как Installed.

## Что хранится в `/workspace`

Entrypoint создаёт и подключает к ComfyUI следующие каталоги:

```text
/workspace/models
/workspace/input
/workspace/output
/workspace/user
/workspace/custom_nodes
/workspace/.cache/pip
```

При старте контейнер восстанавливает зависимости дополнительных и изменённых нод.
Requirements, совпадающие со встроенными в образ, пропускаются. Pip использует
постоянный кэш `/workspace/.cache/pip`; Hugging Face и Torch — свои каталоги
в `/workspace/.cache`.

## Разница между дисками RunPod

### Container Disk

Хранит распакованный Docker-образ и системное окружение. Очищается при Stop. Восстанавливается из GHCR при следующем запуске.

### Volume Disk

Монтируется в `/workspace`, переживает Stop/Start и привязан к одному Pod. Удаляется при Terminate. По данным интерфейса RunPod, стоит $0.10 за ГБ в месяц во время работы и $0.20 за ГБ в месяц во время простоя.

### Network Volume

Также монтируется в `/workspace`, но живёт независимо от Pod и может подключаться к другим Pod. Стоит дешевле обычного остановленного Volume, однако привязывает выбор GPU к конкретному дата-центру. Ранее созданный Network Volume удалён из-за низкой доступности нужных GPU в его регионе.

## Ранее рассмотренная схема внешнего хранения

Ранее рассматривалось объектное хранилище для переносимости между провайдерами:

```text
Docker-образ  -> ComfyUI, PyTorch, Manager, базовые ноды
Object Storage -> модели, workflow, настройки, важные результаты
Volume Disk   -> быстрый локальный кэш текущего Pod
```

Кандидаты для Object Storage: Cloudflare R2 или Backblaze B2. Dropbox не выбран как основной вариант для большой коллекции моделей. Хранилище ещё не настроено. Сейчас основной вариант для RunPod — Network Volume; внешнее хранилище остаётся возможным местом резервных копий.

Object Storage не следует монтировать как основной диск для чтения моделей во время генерации. Правильная схема: скопировать нужные модели на локальный Volume перед работой и синхронизировать результаты после неё.

## Сеть и загрузка моделей

В RunPod нет универсальной кнопки, которая гарантирует быстрый внешний интернет для обычного Pod. Скорость зависит от конкретного хоста, дата-центра и источника модели.

Global Networking создаёт приватную сеть между Pod и не ускоряет загрузку из Hugging Face. High-performance Network Storage относится к скорости хранилища, а не внешнего интернета.

Для Hugging Face предпочтителен актуальный `huggingface_hub` с `hf_xet`. Режим `HF_XET_HIGH_PERFORMANCE=1` требует много RAM и пока не включён.
